## 1. Target and restrictions

This model covers the authenticated merchant application shell, resumable setup metadata, basic products, categories, ordering, availability, catalogue preview, and private product-image upload planned in Phase 2.

Phase 2 remains local/private and synthetic. It excludes public storefronts, customer/order/payment data, delivery zones, payment instructions, real vendors, support access, messaging channels, public object delivery, production hosting, analytics, and AI processing. Product variants/options, stock tracking, maximum-order rules, and product-specific delivery restrictions remain deferred unless the roadmap and this model are explicitly updated. Those capabilities require later acceptance and, where applicable, threat-model updates.

## 2. Architecture and trust boundaries

```text
Merchant browser
  -> Next.js server actions/routes (untrusted input boundary)
  -> fresh Supabase Auth + PieShop application-session verification
  -> self-authorizing Postgres RPC/RLS boundary
  -> tenant-owned setup/catalogue rows

Merchant browser
  -> authenticated upload endpoint
  -> signature/size/dimension validation and decode/re-encode boundary
  -> private Supabase Storage object path generated by the server
  -> tenant-owned product-image metadata

Platform owner control plane -- no implicit route --> merchant setup/catalogue
```

Supabase Auth, Postgres, and Storage are external trust dependencies. Mailtrap remains limited to synthetic authentication mail and is not a catalogue dependency.

## 3. Actors, assets, and entry points

Actors: merchant owner, future merchant staff, platform owner, unauthenticated visitor, cross-tenant merchant, malicious file sender, compromised browser/session, and failed/misconfigured provider.

Assets: tenant identity and membership, business contact/settings metadata, catalogue/product/category data, prices, availability, private images, storage paths, audit evidence, session credentials, and merchant-content privacy.

Entry points: merchant navigation and forms, server actions/RPCs, preview queries, image upload endpoint, Storage policies, filenames/metadata, and application-session cookies.

## 4. Invariants

- Every merchant-owned row and object is bound to one `business_id`; authority is derived server/database-side from the fresh authenticated identity and active session, never accepted from client tenancy claims.
- Platform roles provide no catalogue access. Support requires a later explicit merchant grant.
- Suspended/archived merchants and revoked/expired sessions cannot read, mutate, preview, or upload.
- Database relationships enforce same-business ownership; a tenant cannot attach its product to another tenant's category, image, or future related record.
- Money is integer minor units in the business currency; timezone is a validated IANA identifier; UTC instants remain canonical.
- Products and images are archived/replaced, not hard-deleted when history may reference them.
- Uploads accept only reviewed raster input types, are private, server-path-generated, signature-validated, bounded, decoded/re-encoded, and stripped of metadata before persistence. SVG and other active/document formats are rejected.
- Authenticated HTML and server-action responses carrying merchant content are private/no-store and must not leak through shared caches, URL parameters, referrers, or error pages.
- Public/browser responses and logs never expose credentials, storage signing material, cross-tenant identifiers, contact values, or provider internals.
- Mutations are server-authorized, validated, idempotent where retries are plausible, and append-only audited with the real actor.

## 7. Residual risks and blockers

- Process-local throttling, no MFA/AAL2, synthetic manual Auth provisioning, and private/local exposure remain accepted only if the owner renews that acceptance for Phase 2.
- A merchant with a compromised mailbox/browser can be impersonated at AAL1. No real vendor or real data may be introduced.
- Supabase processes encrypted-at-rest database/storage content. Basic catalogue text and prices are not application-layer encrypted in Phase 2. Business contact values may identify a person, so only synthetic contact values are permitted; field-level classification, minimisation, masking, export/backup handling, and encryption must be resolved before any real-vendor use. Customer, address, payment, and bank data remain prohibited.
- Image parsing is not yet safe because no decoder/re-encoder has been selected; Part 2.3 is blocked until that dependency review.
- Short-lived signed image reads still create bearer URLs. Their maximum lifetime and caching policy must be fixed during the Part 2.3 design review; no signed URL may enter logs, audit events, analytics, or Telegram.
- Production, staging, public preview, real-vendor demo, and real personal data remain blocked.
